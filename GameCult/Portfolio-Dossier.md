## Void Thesis


The old web connected pages. GameCult is trying to connect surfaces: stateful rooms where work, support, governance, agents, and tools can meet without pretending that a private chat log is an institution.


<aside class="portfolio-dossier-callout orange">
<strong>Void says</strong>

The portfolio is not a pile of unrelated projects. It is a pressure rig. Every repo forces the shared substrate to answer a different question: who owns truth, who may act, what changed, who paid, who worked, who gets credit, and what surface can a human actually use?
</aside>



### The machine
- <span class="portfolio-term">Bifrost</span> records work, patronage, motions, ledgers, receipts, voting power, and reward pressure.- <span class="portfolio-term">CultMesh</span> distributes typed state without flattening authority.- <span class="portfolio-term">Eve</span> renders shared operational surfaces across web, desktop, mobile, game, and overlay consumers.- <span class="portfolio-term">Sai</span> turns those surfaces into navigable public story.- <span class="portfolio-term">Epiphany</span> keeps agents from waking up in the middle of the work with no map and a confident little chainsaw.



### The public spell


The gamer-market sentence is blunt:

<aside class="portfolio-dossier-callout orange">
<strong>Public spell</strong>

Play the games. Support the worlds. Your support becomes governed voting power.
</aside>

Microtransactions become scoped patron events. Patron events become effective points. Effective points pass through the log-power curve. Votes remain bounded by project governance. A skin purchase does not buy a balance patch. It does make the player part of the governed support body instead of a wallet with a health bar.


### The log-power spine


$$
  voting_weight = 1 + \log_{base}(\max(1, effective_points))
$$

Base 2 is sharp. Base 10 is flat. The base is not a constant. It is a political agreement. The platform asks: how flat do we want the hierarchy to be?



## Eve And The Surface Web


Eve is not a dashboard. Eve is a renderer for shared, typed, inspectable control surfaces.

<aside class="portfolio-dossier-callout blue">
<strong>Surface contract</strong>

**Surface pipeline**

provider-owned state $\to$ CultUI semantic tree $\to$ Eve projection $\to$ local renderer $\to$ command intent $\to$ provider acceptance $\to$ updated state
</aside>

The web made documents portable. Eve makes operational interfaces portable.


<section class="portfolio-dossier-card">
<h4>Eve Surface-Web Stack</h4>
<table class="portfolio-dossier-table">
<tbody>
<tr><th>Provider</th><td>Owns state, permissions, commands, and acceptance.</td></tr>
<tr><th>CultUI Tree</th><td>Declares semantic controls, bindings, layout intent, and provenance.</td></tr>
<tr><th>Eve</th><td>Projects one surface contract into web, desktop, mobile, game UI, and overlays.</td></tr>
<tr><th>Renderer</th><td>Chooses native affordances without stealing authority from the provider.</td></tr>
</tbody>
</table>
</section>



### CultUI semantics


A surface should describe meaning, not smuggle executable UI:- stable widget ids- typed bindings- command routes- layout intent- permission hints- health and provenance- local renderer affordances


Web can render it as DOM. Desktop can render it as native controls. Mobile can render it as touch-first panels. Unity can render it as runtime UI. Sai can render it as a story room.


<aside class="portfolio-dossier-callout orange">
<strong>Void says</strong>

If Eve streams arbitrary DOM, we built remote desktop with better incense. If Eve streams CultUI surfaces, we built a new public interface grammar. Choose the second thing.
</aside>




## Bifrost Patronage And Power


Bifrost is the financing primitive because Bifrost can recognize support and contribution directly. The old world asks whether a patron gets equity. The GameCult machine asks what scoped support event entered the ledger and what governance curve transforms it.


<section class="portfolio-dossier-card">
<h4>Value Furnace</h4>
<table class="portfolio-dossier-table">
<tbody>
<tr><th>Input</th><td>Patronage, game spend, verified work, support, and risk.</td></tr>
<tr><th>Normalization</th><td>Project-local rules turn events into effective points.</td></tr>
<tr><th>Governance</th><td>Log-power voting keeps power legible without pretending all support is equal.</td></tr>
<tr><th>Output</th><td>Priority, reward pressure, credit, receipts, and scoped voting weight.</td></tr>
</tbody>
</table>
</section>



### What counts
- direct patronage- recurring support- game microtransactions declared as patronage- accepted work artifacts- continuous care work- project-specific contribution- global substrate contribution



### What does not count directly


Private enthusiasm does not count directly. Discord volume does not count directly. Raw revenue counters do not count directly. They create evidence or support events. Bifrost owns the ledger, not the nearest loud surface.


### The gamer pitch


Buy into a GameCult world and you become a patron of that world. Your purchase can become scoped patron credit. Scoped patron credit becomes voting weight through the log curve. The player gets a voice without becoming a tiny sovereign with a cash shop crown.

## Sai Homepage Pipeline


The TeX dossier is the ceremonial artifact. Sai is the playable public route.


### Target structure
- Each portfolio project becomes a VN room.- Each projection ladder becomes a DOM card.- Each governance claim becomes a Bifrost receipt panel.- Each project can link to its canonical page, repo, and dossier chapter.- Eve can later render the same portfolio data as a live dashboard.



### Sai asset contract


The folder includes \texttt{sai/portfolio-tour.ink} and \texttt{sai/portfolio.visual-manifest.json}. They are seeds, not final compiled assets. The intended build path is:

<aside class="portfolio-dossier-callout orange">
<strong>Pipeline</strong>

`data/portfolio.yaml` $\to$ TeX chapters $\to$ Sai Ink routes $\to$ homepage VN
</aside>


<aside class="portfolio-dossier-callout orange">
<strong>Void says</strong>

Do not maintain the PDF, homepage VN, and future Eve dashboard as three unrelated beautiful lies. One portfolio ledger. Many surfaces. Same machine.
</aside>



### TeX In Browser


Sai needs a TeX surface, not just a PDF link.

The portfolio dossier should compile as ceremonial PDF, but Sai also needs to embed TeX-authored material in-browser as VN cards, projection panels, formulas, and page-like dossier spreads. That gives the homepage the same authority surface as the document without forcing visitors to leave the VN.


#### Renderer split
- <span class="portfolio-term">Math fragments</span>: render with a client-side math renderer such as KaTeX for formulas and compact notation.- <span class="portfolio-term">Dossier spreads</span>: render precompiled page images or HTML fragments generated from TeX during the site build.- <span class="portfolio-term">Live cards</span>: render structured portfolio data through Sai DOM cards when the card is semantic rather than typographic.


The browser should not run arbitrary TeX as an execution surface. TeX is too powerful and too weird to invite into the house unsupervised. The coherent path is build-time compilation plus a safe runtime fragment renderer.


#### Sai contract


Sai should learn a new card source kind:

<aside class="portfolio-dossier-callout blue">
<strong>Surface contract</strong>

`tex-fragment`: safe inline/block math or short TeX panels rendered in browser.

`tex-page`: precompiled dossier page image or HTML fragment emitted by the build.

`portfolio-card`: structured claim data rendered as local DOM.
</aside>

The VN route can then say: show Eve's projection formula, show Bifrost's voting curve, show the portfolio page spread, then offer the project room choices.


<aside class="portfolio-dossier-callout orange">
<strong>Void says</strong>

Sai should make TeX walk around the room, not nail a PDF to the wall and call it interactive.
</aside>

It should eventually own:- project id- display name- portfolio family- homepage room- thesis- proof needed- projection ladder- Sai speaker and scene hints- Bifrost scope id- canonical page and repo links


The current TeX files are hand-authored from that shape. The next cut should generate the repetitive project chapters and Sai seed routes from the data file. Manual duplication is tolerable for a first altar sketch. It is not allowed to become architecture.
